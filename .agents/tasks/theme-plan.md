Design decisions (made here, grounded in the above):
1. **Theme attribute goes on `document.documentElement` (`<html>`)**, set as `data-theme="dark"` / removed for light. Rationale: `getComputedStyle(document.documentElement)` then reliably resolves the active custom-property values for the chart, and sticky header/body backgrounds all inherit from the root. The task allows html or body; html is chosen for the getComputedStyle read path.
2. **Theme logic lives in a new `ThemeManager` static-ish class** mirroring `StorageManager`'s shape (static methods, storage guarded via a `isStorageAvailable()`-style try/catch). Rationale: matches existing architecture (ES6 classes, static where state is shared/stateless) and the `expense-tracker-*` key convention. Storage key: `expense-tracker-theme`.
3. **Chart theme-awareness: read colors from CSS custom properties via `getComputedStyle`** at build time, and re-apply on toggle via `chartInstance.update()`. Rationale: single source of truth (the CSS tokens), no duplicated color constants, satisfies "compute colors from the active theme." Category segment colors (`#FF6384/#36A2EB/#FFCE56`) are kept as-is — they already read acceptably on dark; only legend/tooltip/segment-border text colors change.
4. **Wiring: `ThemeManager.init()` is called inside `initApp()`**, after `uiManager.initialize()` so the chart instance exists when the first theme application tries to refresh it; the toggle's click handler calls both the theme apply and a chart refresh. Rationale: chart must exist before theme application touches it, and `initApp` is the single documented bootstrap.
