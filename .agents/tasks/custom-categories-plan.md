# Implementation Plan — Custom Categories

Feature: let users add (and delete unused) custom expense categories, persisted in Local Storage, with auto-assigned accessible colors that drive both the badges and the pie chart. Pure vanilla JS, no build step, no new dependencies. All edits are in place in three files:

- `js/app.js`
- `index.html`
- `css/styles.css`

## Design decisions (grounded in the current code)

These are decided here so the implementer never has to choose. One or two sentences of rationale each.

1. **CategoryManager is an instance-based class with injected storage**, mirroring `TransactionManager` (`new TransactionManager(StorageManager)`). It owns the custom-category list, merges built-ins + customs into the active list, assigns colors, and persists. Rationale: matches the existing dependency-injection pattern and keeps storage access testable/stateless.

2. **Built-ins stay a constant; customs are dynamic.** `CategoryManager.BUILT_INS = ['Food', 'Transport', 'Fun']` are permanent, non-deletable, and always first in the active list. The active list is `[...BUILT_INS, ...customNames]`. Rationale: the requirement says the three built-ins are permanent defaults.

3. **Persistence key + shape** follow `StorageManager.saveTransactions` exactly: key `expense-tracker-categories`, payload `{ version: '1.0', categories: [ { name, color } ] }`. Only CUSTOM categories are stored (built-ins are implicit, so renaming a built-in color later never fights a stale stored copy). Load validates structure, drops malformed entries, and returns `[]` on any failure. Never throws. Rationale: identical versioned-payload + try/catch + never-throw contract as transactions.

4. **Color palette (8 hues), white-text legible in both themes.** Built-ins keep their current look by mapping to the existing CSS tokens' hex values: Food `#dc2626` (red), Transport `#2563eb` (blue), Fun `#7c3aed` (purple). Custom categories are assigned, in order, from this accessible palette (all verified ≥4.5:1 against white text, so white badge text and dark-theme parity hold — same bar the CSS comments already document for the built-ins):
   - `#dc2626` red, `#2563eb` blue, `#7c3aed` purple (reserved for built-ins),
   - `#047857` green (4.54:1), `#b45309` amber-brown (4.52:1), `#be185d` pink (5.41:1), `#0f766e` teal (4.76:1), `#4338ca` indigo (7.0:1).
   Assignment: next unused palette color by index; when the palette is exhausted, cycle back to the start (`palette[index % palette.length]`). A color is stored WITH each custom category at creation so it stays stable across reloads even if the palette changes. Rationale: a fixed small palette keeps every badge white-text legible without per-name CSS; storing the color makes it stable.

5. **Badge coloring becomes data-driven, not per-name CSS classes.** Replace the `category-${name}` class dependency: both `TransactionListComponent.createTransactionElement` and `MonthlySummaryComponent.createMonthElement` set the badge background from the category's assigned color via an inline style (`element.style.backgroundColor = color`) and keep white text. A generic `.category-badge` class carries the shared shape/typography (previously duplicated in `.transaction-category` / `.monthly-category`). Rationale: arbitrary names can't have pre-written CSS classes; inline background from the stored color works for any name and keeps the chart and badge in sync.

6. **Chart reads colors from CategoryManager, not a hardcoded map.** `ChartComponent.categoryColors` object is removed; the component resolves each slice color by calling into CategoryManager (passed a color-lookup at construction/update time). Rationale: pie slices must match badge colors for arbitrary categories.

7. **`getCategoryTotals` / `getMonthlySummaries` iterate the dynamic active list.** `TransactionManager` gains a reference to the active-category source (injected `CategoryManager`) and seeds buckets from the active list instead of the static `CATEGORIES`. **Zero-spending behavior:** keep seeding every ACTIVE category at zero in totals (complete totals), but the chart continues to hide all-zero/entirely-empty states exactly as today (`isAllZero`) and a category with 0 total simply renders as a 0 slice that Chart.js draws as nothing — matching current behavior where Food/Transport/Fun always appear in totals. Rationale: preserves the current "totals complete, chart sensible" behavior while swapping the static list for the dynamic one.

8. **Validation uses the dynamic list without breaking the static call sites.** `TransactionManager.validateTransaction(itemName, amount, category)` is called statically from two places (`UIManager.handleFormSubmit` and `TransactionManager.addTransaction`). Add an optional 4th parameter `activeCategories` (defaulting to `TransactionManager.CATEGORIES` so nothing breaks if omitted); both call sites pass the live active list from CategoryManager. Rationale: minimal, backward-compatible change to a static method rather than a risky signature overhaul.

9. **New-name validation rules (CategoryManager.validateName):** trim; reject empty; max length **30** chars (documented limit); reject case-insensitive duplicates of any active category (built-in or custom); reject the reserved sentinel value used by the dropdown. Returns `{ valid, error }` with a user-facing message. Rationale: the requirement asks for these exact guards with a documented cap.

10. **Add-category UX = inline accessible flow via the existing dropdown sentinel**, not `prompt()`. The `<select>` gets a final `<option value="__add_new__">+ Add new category…</option>`. Selecting it reveals an inline, keyboard-usable text input + confirm/cancel buttons (hidden by default, `is-hidden`), with its own `role="alert"` error span. On confirm: validate, add+persist, re-render the dropdown, select the new category, hide the inline input. On cancel/empty: revert the select to the previous value. Rationale: `prompt()` is allowed but the inline input is more accessible and consistent with the app's existing form patterns; it reuses the error-span + `is-hidden` conventions already in the code.

11. **Delete UX = a minimal "Manage categories" disclosure** listing custom categories only, each with a delete button. Deleting is allowed only when no transaction uses that category (checked against `TransactionManager.getTransactions()`); otherwise it is blocked with a clear inline message. Built-ins are never listed as deletable. Rationale: smallest accessible surface that satisfies the "delete unused custom only" requirement.

12. **Dropdown + manage-list re-render on every change.** A single `CategoryManager` change notification (callback registered by `UIManager`) re-renders the `<select>` options and the manage list whenever categories are added or deleted, keeping the blank placeholder first and the "+ Add new category…" option last. Rationale: the dropdown must always reflect the current active list from one source of truth.
